# Helpdesk Worklist - App Builder Database Demo

A small Adobe App Builder app demonstrating App Builder Database (ABDB) through
a helpdesk queue. Create tickets, view open work ordered by urgency and age,
claim a ticket as the signed-in user, and deliberately submit invalid input to
see database-enforced validation.

The UI uses React Spectrum inside Adobe Experience Cloud. Three authenticated
Runtime actions perform the database operations; no sample tickets are seeded.

## What this demo showcases

| Topic | Demonstration | Code |
| --- | --- | --- |
| Schema validation | Require title, status, priority, and a BSON Date creation timestamp; reject malformed documents on insert. | [Schema](actions/lib/db.js), [create-ticket](actions/create-ticket/index.js) |
| Partial index | Index priority and creation time only for tickets with `status: 'open'`. | [Index definition](actions/lib/db.js) |
| Explicit `hint` | Select `open_priority_createdAt` using a query containing its open-ticket predicate. | [list-open](actions/list-open/index.js) |
| Sort and projection | Return only worklist fields, ordered by priority then oldest creation time. | [list-open](actions/list-open/index.js) |
| Conditional `findOneAndUpdate` | Claim only an open, unassigned ticket and return its updated document with `returnDocument: 'after'`. | [claim-ticket](actions/claim-ticket/index.js) |
| Deploy hook | Create the validated collection if missing and ensure the worklist index after deployment. | [setup-database](scripts/setup-database.js), [configuration](app.config.yaml) |

Priorities are `1` urgent, `2` normal, and `3` low. The schema allows `open`,
`claimed`, and `closed`; this demo implements creation and claiming, not a full
close/reopen lifecycle.

## Prerequisites

- Node.js 22 or later, npm, and the Adobe I/O CLI (`aio`).
- An App Builder Developer Console workspace with Runtime, App Builder Data
  Services, and an OAuth Server-to-Server credential.
- An Experience Cloud user with access to that workspace's organization.
  Claiming requires a user token with the `openid` scope.

Provisioning activity logs additionally require the I/O Management API and its
`adobeio_api` scope.

## Quick start

### 1. Install and select a workspace

From the repository root:

```sh
cd app-builder-database/helpdesk-worklist
npm install
aio app use
```

Select the workspace you intend to use for the demo. Retain the Runtime
configuration generated by the CLI.

### 2. Configure deployment credentials

Add these values to the app's root `.env`, using the selected workspace's S2S
credential and scopes:

```dotenv
IMS_OAUTH_S2S_CLIENT_ID=<workspace-client-id>
IMS_OAUTH_S2S_CLIENT_SECRET=<workspace-client-secret>
IMS_OAUTH_S2S_ORG_ID=<workspace-org-id>
IMS_OAUTH_S2S_SCOPES=["<workspace-scope>"]
AIO_runtime_namespace=<workspace-runtime-namespace>
DB_REGION=amer
```

The hook reads `AIO_runtime_namespace` or `__OW_NAMESPACE`. Note the spelling:
the separate E2E configuration below requires `AIO_RUNTIME_NAMESPACE`.
Use a JSON array for scopes, and keep credentials out of source control.
Existing environment variables take precedence over `.env`.

### 3. Deploy and open in Experience Cloud

```sh
aio app deploy
```

The manifest enables database auto-provisioning in `amer`, and the post-deploy
hook initializes the collection and index. Check the hook's output for errors.
The database region and package `DB_REGION` are both set to `amer` in
`app.config.yaml`; keep them consistent.
Do not change an existing workspace database's region in place.

Open the **Experience Cloud URL** printed by deployment and select the matching
organization. Opening the standalone CDN page without an Experience Cloud
session does not provide the IMS identity needed by the app.

## Try the demo

1. **Create tickets with mixed priorities.** Create a Normal ticket, an Urgent
   ticket, then another Normal ticket. Add a description to one of them.
   The queue refreshes after creation: Urgent appears first, followed by Normal
   tickets ordered oldest first. IDs, status, timestamps, and ownership are set
   by the server.
2. **Inspect the worklist response.** In the browser's Network panel, inspect
   `list-open`. It returns `_id`, `title`, `status`, `priority`, `createdAt`, and
   `assigneeId`, but not `description`. The UI requests up to 50 tickets; this is
   a bounded worklist, not the entire collection.
3. **Try an invalid create.** Press **Try invalid create**. The same
   `create-ticket` action receives `{ "priority": 99 }`, without a title.
   Expected result: HTTP 422 and **Rejected as expected**. This demonstrates
   ABDB validation, not an application-side field check.
4. **Claim a ticket.** Press **Claim** on an open, unassigned row. The UI shows
   the actual returned document with `status: 'claimed'`, the verified user's
   ID, and a server-generated `claimedAt`. The ticket leaves the open queue.
   A competing claim receives HTTP 409; the UI also refreshes after a conflict.

See **Under the hood** for the schema, index, query, and conditional
update examples. Create more tickets to repeat the demo; there is no reset or
seed action.

## Action API

Actions belong to the `helpdesk-worklist` Runtime package. The UI uses their
generated URLs from `web-src/src/config.json`.

| Action | Request | Success | Expected rejection |
| --- | --- | --- | --- |
| `create-ticket` | POST: `title`, numeric `priority`, optional `description` | HTTP 201 and the created document | HTTP 422 for a genuine schema rejection |
| `list-open` | GET: optional integer `limit`, 1-100; default 50 | HTTP 200, `{ items, limit }` | HTTP 400 for an invalid limit |
| `claim-ticket` | POST: `ticketId` | HTTP 200 and the claimed document | HTTP 409 if missing, assigned, or no longer open |

Example create request:

```json
{
  "title": "Checkout is not working",
  "priority": 1,
  "description": "Payment fails after selecting a delivery option."
}
```

Example claim request, using the ID returned by creation:

```json
{ "ticketId": "<created-ticket-id>" }
```

Unsupported methods return HTTP 405. Invalid claim parameters return HTTP 400.
Missing or rejected authentication returns HTTP 401/403. Operational failures
return HTTP 500; IMS HTTP failures other than 401/403, or a missing user subject,
return HTTP 502 during claiming.

### Authentication and ownership

Requests need `Authorization: Bearer <user-token>` and `x-gw-ims-org-id`.
The deployed `require-adobe-auth` validator checks authentication and organization
authorization. Keep that annotation enabled.

`claim-ticket` resolves the caller through Adobe's
[UserInfo endpoint](https://developer.adobe.com/developer-console/docs/guides/authentication/UserAuthentication/ims#userinfo)
and uses its `sub` as the assignee. Browser-supplied ownership is ignored, and
technical-account identities are rejected. The workspace's separate S2S
credentials are injected into Runtime actions for database access, not for
identifying the human claimant.

## Database initialization and limitations

The [post-deploy hook](scripts/setup-database.js) creates `helpdesk_tickets` with
the validator when the collection is absent, then ensures this index:

```js
createIndex(
  { priority: 1, createdAt: 1 },
  {
    name: 'open_priority_createdAt',
    partialFilterExpression: { status: 'open' }
  }
)
```

The list query includes `{ status: 'open' }` and explicitly hints that index.
It does not retry without the hint if the index is missing or rejected.

Initialization runs after deployment, not during `aio app run` or `aio app dev`.
There is no manual setup command, automatic seeding, or collection reset.
Inspect the index with:

```sh
aio app db index list helpdesk_tickets
```

**Setup limitations:** existing collection validators are left unchanged and are
not checked or migrated. Some credential, connection, and index failures are
logged without failing deployment, so successful deployment alone does not prove
database initialization succeeded. Inspect the hook output and verify the demo
behavior. Incompatible schemas/indexes need explicit remediation; do not drop
existing data to rerun this sample.
A hook failure does not roll back actions that have already been deployed.

If invalid input is unexpectedly accepted, the UI flags the failed validation
demonstration and does not delete the inserted ticket. Fix the collection
configuration before treating the demonstration as successful.

## Local development

Deploy once to initialize the workspace database, then run:

```sh
aio app run
```

This serves the UI locally and uses Runtime actions. Use the Experience Cloud
local-development URL printed by the CLI so the UI receives a signed-in session.
See the [development guide](https://developer.adobe.com/app-builder/docs/guides/development/)
for local-action debugging with `aio app dev`.

## Testing

### Unit tests and build checks

```sh
npm test
npm run lint
npm run lint:ui
aio app build
```

Unit tests mock ABDB/IMS and cover the actions, collection/index initialization,
frontend HTTP contracts, and UI workflows. They do not contact live services or
require credentials. Smaller slices are available with `npm run test:ui`,
`npm run test:setup`, and `npm run lint:setup`.

### Deployed-action E2E

The [E2E suite](e2e/worklist.e2e.test.js) calls real deployed actions, not a
browser. It checks authentication, valid and malformed creation, index metadata,
sort/projection, concurrent claims with one winner, stored ownership, and
exclusion of claimed tickets from the refreshed queue.

Use a **dedicated test workspace** with the app already deployed and initialized.
Start with an otherwise empty open-ticket queue so bounded queries include all
test fixtures. Put that workspace's credentials in the ignored `e2e/.env`:

```dotenv
AIO_RUNTIME_NAMESPACE=<test-workspace-runtime-namespace>
E2E_IMS_TOKEN=<current-user-access-token>
IMS_OAUTH_S2S_CLIENT_ID=<test-workspace-client-id>
IMS_OAUTH_S2S_CLIENT_SECRET=<test-workspace-client-secret>
IMS_OAUTH_S2S_ORG_ID=<test-workspace-org-id>
IMS_OAUTH_S2S_SCOPES=["<test-workspace-scope>"]
```

The user token must have `openid` and access to the selected organization.
An S2S token cannot substitute for the human caller. Existing environment
variables take precedence over this file; ensure they target the test workspace.

```sh
RUN_E2E=1 npm run e2e
```

Keep `RUN_E2E=1` in the command, not the file: it is checked before loading
`e2e/.env`. Without opt-in or required credentials, the suite fails explicitly.

E2E creates its own tickets and deletes only their recorded IDs in `afterAll`,
including unexpectedly accepted malformed input. Cleanup is verified and failures
fail the suite. It never drops a collection or deploys the app. A terminated
process or lost create response may leave tickets requiring manual cleanup;
valid fixture titles carry a unique `e2e-` prefix.

The suite does not cover every schema rule in isolated scratch collections or
prove redeployment compatibility. Those are separate integration checks.
