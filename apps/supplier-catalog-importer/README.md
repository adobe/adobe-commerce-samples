# Supplier Catalog Importer

A development-only App Builder Database tutorial: import a supplier catalog into
staging, review products, and apply subsequent feeds. Its PIM-style catalog admin
console doubles as an interactive tutorial: initialize three suppliers, mutate
their records, then inspect the public JavaScript SDK calls behind each action.
The React Spectrum UI runs in Experience Cloud Shell or through a loopback-only
local database bridge. Do not use real supplier/customer data or deploy this
sample as a production ingestion system.

Follow the [interactive walkthrough](#interactive-walkthrough) to initialize sample
data, manage products, import supplier feeds and review pending products. Use
**Database explorer** to inspect saved records and **What happened?** to understand
the SDK calls behind each action. Initialization and product changes persist
across sessions, so you can return and continue exploring.

## What you will learn

| Capability | Where to read / try it |
| --- | --- |
| Create, find, update, delete | [`actions/lib/catalog.js`](src/dx-excshell-1/actions/lib/catalog.js): `insertOne`, `findOne`, `updateOne`, rejected-only `deleteOne` |
| Sort and projection | `list`: `find().sort({ updatedAt: -1, sku: 1 }).project(...)`, 50 rows per page |
| Supplier/SKU upsert | `upsert`: `updateOne` with `upsert: true`, `$set` and `$setOnInsert` |
| Return the saved review | `save-review`: `findOneAndUpdate`, `returnDocument: "after"`, `includeResultMetadata: false` |
| Batched initial insert | `writeBatches`: sequential `insertMany` calls, at most 50 documents each |
| Batched mixed feed | `writeBatches`: `bulkWrite` containing upserts and update-only discontinuations |
| Lazy iteration | `scanPending`: `for await...of` on a paged `find()` cursor, not `toArray()` |
| Multiple collections and unique indexes | [`actions/lib/structure.js`](src/dx-excshell-1/actions/lib/structure.js), shared by initialization and the deploy hook |
| Repeat-safe seed initialization | [`actions/lib/workbench.js`](src/dx-excshell-1/actions/lib/workbench.js), three suppliers and nine products from [`examples/seed-data.json`](examples/seed-data.json) |

These are public [`@adobe/aio-lib-db`](https://www.npmjs.com/package/@adobe/aio-lib-db)
APIs, not direct MongoDB connections. See the
[Database Storage guide](https://developer.adobe.com/app-builder/docs/guides/app_builder_guides/storage/database).
The app pins SDK 1.0.4 so its cursor and after-image contracts are reproducible.

## Prerequisites

- Node.js 22+ and the [Adobe I/O CLI](https://developer.adobe.com/app-builder/docs/get_started/).
- An App Builder **development** project/workspace with Runtime and Database
  access/entitlement, **App Builder Data Services API**, and OAuth Server-to-Server
  credentials for that workspace.
- The database API scopes `adobeio.abdata.read`, `adobeio.abdata.write`,
  `adobeio.abdata.manage` on the workspace credentials. Preserve any additional
  scopes supplied by Developer Console.
- Developer access to that workspace and an authenticated Experience Cloud Shell
  session in the same organization.

### Setup and deploy

Run commands from this directory:

```sh
npm ci
cp env.dist .env
aio auth login
aio app use
```

Select your development workspace. Fill in the ignored `.env`:

| Variable | Purpose |
| --- | --- |
| `AIO_RUNTIME_NAMESPACE`, `AIO_RUNTIME_AUTH` | The selected workspace's Runtime values; used by CLI tooling |
| `DB_REGION` | Provisioned database region; default `amer`, also `emea`, `apac`, `aus` |
| `DB_CLIENT_ID`, `DB_CLIENT_SECRET`, `DB_ORG_ID`, `DB_SCOPES` | Same workspace's S2S credentials, used only server-side by the local bridge and setup script |

**Confirm the namespace and credential workspace match before continuing.** Never
commit `.env`, Console exports, or tokens. Do not copy DB credentials into web code.
The setup hook and local bridge also accept `AIO_runtime_namespace` and
`IMS_OAUTH_S2S_*` values generated by `aio app use`, including JSON-array scopes;
you do not need to duplicate those credentials under the `DB_*` names.

Provisioning is an explicit resource-creation step, not a deploy-hook side effect:

```sh
aio app db provision
aio app db status
# Wait until status is PROVISIONED.
```

The I/O Management API's `adobeio_api` scope is also needed for provisioning
activity logging. If provisioning reports an activity-log 403, verify actual
database status before retrying resource creation.

### Try the interactive app locally

After provisioning and filling `.env`, run:

```sh
npm run dev
# Open http://127.0.0.1:8787 (not localhost).
```

This builds the app and starts [`scripts/local-server.js`](scripts/local-server.js).
The bridge uses the **real workspace database**. It serves the optimized UI and
delegates requests to the same validated service as Runtime.
S2S credentials stay in the Node process; none are sent to the browser. The server
binds only to `127.0.0.1`, requires its exact Host and same-origin requests, and
requires a non-simple API header. Never expose it through a public tunnel or
reverse proxy. Stop it with Ctrl+C; use `CATALOG_PORT=8788 npm run dev` if needed.
Rebuild/restart after source changes.

On startup, the app checks database-backed initialization status before offering
setup, so returning sessions open the existing catalog without flashing an
initialization prompt. Connection failures offer a read-only retry, not setup.
For a new workspace, a centered welcome page explains the sample data, database
changes and persisted setup above its only action, **Initialize app**. That button
creates missing collections/indexes and saves the repository's predefined
supplier/catalog data.
It does **not** provision a database. Local `aio app run`/`aio app dev` do not run
the post-deploy setup hook or auto-provision this sample's database.

### Deploy to Experience Cloud Shell

```sh
npm run lint
npm run format:check
npm run build
aio app deploy --no-build
```

The post-deploy hook creates `supplier_catalog_suppliers` with unique
`supplier_id_unique: { supplierId: 1 }`, plus `supplier_catalog_staging` with
unique `supplier_sku_unique: { supplierId: 1, sku: 1 }`. It does not seed products;
the UI's initialization button does that.
Repeated setup preserves records and repeats the identical index definition.
Duplicate existing records, incompatible indexes, permission failures and
unprovisioned databases fail setup; they are **not** treated as success. It never
drops indexes, collections or databases. If setup fails, actions/web assets may
already be deployed: correct the workspace/access/data issue, run `npm run setup-db`,
then retry deployment if needed. Do not use the app before setup succeeds.

Open the **Experience Cloud Shell URL printed by the CLI**, not the asset URL.
The deployed action remains authenticated; the local bridge does not weaken its
gateway policy. Shell bootstrap follows the documented
[`init` callback, `ready` and `configuration` lifecycle](https://developer.adobe.com/app-builder/docs/guides/app_builder_guides/exc_app/aec-integration).
Locale and token updates merge into the existing Shell context.

### Authentication: two different responsibilities

The UI sends the current Shell bearer token to a web action protected by
`require-adobe-auth: true`. Runtime's `include-ims-credentials: true` injects the
workspace S2S credentials; `generateAccessToken` obtains the DB token server-side.
The action only forwards the injected auth metadata to that helper, not arbitrary
top-level client credential fields. The SDK derives its namespace from Runtime's
`__OW_NAMESPACE`, never a browser `namespace` parameter.

Unlike a caller-token database model, data access here is **workspace-shared**.
Supplier IDs organize records; they are **not tenant authorization boundaries**.
There are no per-supplier ACLs or reviewer roles. Do not expose this shared,
authenticated mutation endpoint to untrusted users. A production app needs
explicit caller/org/role authorization, audit records and supplier ownership.

## Interactive walkthrough

1. **Initialize app.** Create Acme Home (`acme`), Nordic Living (`nordic`), and
   Terra Outdoors (`terra`), with three products each. Initialization uses
   insert-only upserts and only marks readiness after seed writes succeed.
   Reloading discovers persisted readiness. Once initialized, repeating setup
   does not overwrite edits or restore deliberately deleted products.
   The **Database initialization** section in **Learn by doing** stays available
   independently of Recent activity, including after reload. **How initialization
   works** explains server-side ABDB client creation, collection/index setup,
   insert-only seed writes, readiness markers and client cleanup. It is a read-only
   reference, not a way to rerun setup. The guide and initialization activity
   lesson share credential-free SDK excerpts.
2. **Inspect the store.** Open the **Database explorer** tab to browse the two
   collections in a read-only table and open each document as JSON. Filter by supplier, exact
   SKU and review status, choose a sort order, and page through 25 documents at a
   time. **Schema & indexes** shows the selected collection's document model and
   actual database indexes. Select the **Suppliers** collection to browse supplier
   profiles and open their JSON documents; there are no separate database
   shortcuts above the workspace tabs. The **Supplier** picker selects the
   supplier for catalog actions. The same SKU may appear under different
   suppliers; this is application scoping, not tenant authorization.
3. **Create and find.** In **Catalog workspace**, open **Add product**, select
   **Generate product details**, optionally edit them, then **Create product**.
   Open the separate **Find product** tab to look up a SKU.
   Generated SKUs use UUIDs so subsequent imports do not collide with seed data.
   Selecting a table row retrieves its details and opens Find product. The Add
   product draft and Find lookup are separate from the loaded existing record.
   Update, Review and Delete show the loaded SKU as read-only, so typing another
   lookup or a failed Find cannot retarget edits to a different product.
4. **Update.** In **Update product**, change name/price and select
   **Update attributes**, which resets review status to pending. There is no
   separate Upsert product tab: mixed supplier feeds demonstrate updating
   existing SKUs or inserting missing ones while preserving existing `createdAt`.
5. **Review and delete.** In **Review product**, choose Approved or Rejected and
   **Save review**. Use **Delete product** for confirmed rejected-only deletion.
   The screen renders the saved after-image from `findOneAndUpdate`, not a second
   read. Only a rejected record can be deleted; other delete attempts explain the
   refusal rather than being permanently greyed out.
6. **Import in batches.** In **Import studio**, **Generate initial catalog**
   creates editable JSON (75 rows by default), then **Import initial catalog**
   runs two `insertMany` batches: 50 + 25. **Generate mixed feed** builds updates,
   new upserts, and a discontinuation from available products; **Apply mixed
   feed** uses bounded `bulkWrite` calls. Generate again before another initial
   import rather than replaying duplicate SKUs.
7. **Stream reviews.** In **Review queue**, **Scan pending reviews** uses
   `for await...of`, counts at most 1000, retains 20 preview SKUs, and explicitly
   reports truncation. It never loads the entire catalog into an array.
8. **Understand every action.** **Recent activity** describes the last eight
   successful user actions in plain language, such as "Added product DEMO-123".
   Its adjacent **What happened?** button opens public SDK calls, the saved
   result, and separately identified follow-up reads. Each explanation appears
   before its code, with JavaScript/JSON syntax coloring throughout read-only
   dialogs, schema/index views and scan results. **Show client setup** expands
   the shared server-side token, `init`, `connect` and `close` lifecycle without
   repeating it above every operation by default. A request reuses one client
   for its SDK calls; UI follow-up reads open their own clients. All displayed
   setup code uses parameter references, never credential or token values.
   Validated input is no
   longer shown as a separate section; server validation is unchanged.
   Mutations automatically refresh the list. A successful write remains visible
   if refresh fails, with a warning not to blindly repeat it. Review-scan and
   explorer snapshots are invalidated before a write that might partially
   commit. Confirmed deletions are removed from the local selection and table
   even when the subsequent refresh fails.

Buttons are temporarily disabled only while a request is running, not because
the sample requires hardcoded auth or preselected data. Invalid inputs and
rejected-only deletion rules are enforced server-side and explained visibly.
## Action contract

The action is `supplier-catalog/catalog`; all web calls use POST JSON.
Every operation requires `operation`; catalog mutations/lookups also require
`supplierId`. The read-only `browse` operation accepts only the two collection
aliases and an allowlisted set of exact-match filters and sort choices.
No arbitrary collection, query operators, updates or projection are accepted.

| Operation | Additional fields | Result |
| --- | --- | --- |
| `status` / `suppliers` | None | Persisted initialization status and predefined suppliers |
| `initialize` | None | Ensure structure, seed if needed, return persisted readiness |
| `schema` | None | Application-defined fields and actual indexes for both collections |
| `browse` | `collection: "catalog" \| "suppliers"`; optional `supplierId`, catalog-only `sku`/`reviewStatus`, `sortBy`, `sortDirection: "asc" \| "desc"`, `offset` | Up to 25 application documents, page metadata, and next-page availability; no collection total |
| `create` | `sku`, `product: { name, price }` | Created staging product |
| `get` | `sku` | Product or 404 |
| `list` | Optional integer `offset` (0-10000), `reviewStatus` | Up to 50 projected rows |
| `update` | `sku`, `product` with name and/or price | Matched/modified counts, or 404 |
| `upsert` (API example only) | `sku`, `product: { name, price }` | SDK update/upsert result; the UI teaches upserts through mixed feeds |
| `save-review` | `sku`, `reviewStatus` | Saved after-image, or 404 |
| `delete-rejected` | `sku` | Deleted count, or 409 if not rejected/not found |
| `initial-import` | `rows: [{ sku, name, price }]` | Completed batches/rows and write counts |
| `sync-feed` | `rows: [{ type: "upsert", sku, name, price }, { type: "discontinue", sku }]` | Completed batches/rows and aggregate counts |
| `scan-pending` | None | `scanned`, bounded `preview`, `truncated`, `scanLimit` |

Example web invocation; use the action URL printed by the CLI and your current
Shell/IMS token in an environment variable (never a source file):

```sh
curl --fail-with-body "$CATALOG_ACTION_URL" \
  -X POST -H "Authorization: Bearer $IMS_TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'x-ow-extra-logging: on' \
  --data '{"operation":"save-review","supplierId":"acme","sku":"MUG-001","reviewStatus":"approved"}'
```

Successful responses are `{ "operation": "...", "result": ..., "lesson": { "title": "...", "code": "...", "input": ..., "note": "..." } }`. Errors have
an `error` field. Validation is 400 (oversize feed 413), missing products 404,
non-rejected deletion 409, and unexpected database/write failures 500. Service
401/403/429/503 codes are preserved. A duplicate-key create/import fails visibly;
the sample does not parse backend error strings to classify it as a 409.
Action errors/logs do not include raw SDK errors, headers, credentials or feed data.

## Data model and limits

**Yes, App Builder Database supports multiple collections.** Each project
workspace has one isolated database; this app stores suppliers separately from
their staged products. Records link through `supplierId`. The unique indexes
enforce identity, but there is no automatic foreign-key relationship or enforced
relational schema. The schema screen combines the model in `structure.js` with
live `getIndexes()` results.

```js
{
  supplierId: "acme", sku: "MUG-001", name: "Stoneware mug", price: 12.5,
  reviewStatus: "pending", // pending | approved | rejected
  discontinued: false,
  createdAt: "2026-01-01T00:00:00.000Z",
  updatedAt: "2026-01-01T00:00:00.000Z"
}
```

The database has its own `_id`; projections deliberately omit it. Identity is
`(supplierId, sku)`, enforced by the unique index, not a check-then-insert.
Prices are finite non-negative demo USD numbers with at most two decimals, capped
at 1,000,000. Use integer minor units/decimal types and explicit currencies for
real financial work. Identifiers are 1-64 letters/numbers/underscore/hyphen
(first character alphanumeric); names are non-empty, at most 200 characters.

**Demo teaching limits, not service maximums:**

- At most 500 feed rows and 512 KiB serialized rows per invocation; all rows,
  duplicate SKUs and field types are validated **before the first write**.
- Sequential batches of 50 database writes/documents. The request's bounded input
  array is still held in memory: batching writes is not streaming upload parsing.
- The web platform's overall request/response limit is 1 MB; split large catalogs
  across invocations. Do not simply raise limits for production ingestion.
- Pending scan processes up to 1000 matching records plus one lookahead to detect
  truncation, using cursor batch size 50 and preview size 20. `truncated: true`
  means the returned count is not a full catalog total. Large recurring scans need
  resumable jobs. Offset list pages may shift under concurrent writes.
- Database explorer reads at most 26 documents (25 plus one lookahead), omits
  internal `_id` and fields outside the application model, and allows offsets
  0-10000 in steps of 25. Catalog sort choices are `updatedAt`, `sku`, `name`,
  `price`, `reviewStatus`, `supplierId`; supplier choices are `name`, `supplierId`,
  `createdAt`. Stable identity tie-breakers are appended. Pages can still shift
  under concurrent writes; narrow filters if the browse limit is reached.

### Partial writes and retries

`ordered: true` stops a failed batch at its first error. Earlier rows in that
batch and all completed batches may already be committed. There is **no
transaction or rollback across batches**. A failed response reports `progress`
with `rowsCompleted`, `batchesCompleted`, `failedBatch` and
`failedBatchMayHaveWrites: true`. Counts cover **only fully completed batches**,
not the unknown partial failed batch.

Initial `insertMany` import is intentionally **not idempotent**. Inspect records
after a failure; do not blindly retry the whole initial import. Reconcile with
an explicit upsert feed after inspecting what was saved. Mixed feeds converge on
supplier/SKU identity, but replaying also changes `updatedAt` and resets reviews.
Do not retry over concurrent reviewer edits without a conflict policy. No
automatic retries are implemented. An aborted browser fetch does not roll back
an action that already started.
